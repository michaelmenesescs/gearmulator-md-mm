## A2 - The capture path, and how to make frames cheaper

Paths below are relative to /Users/michaelmeneses/gearmulator-md-mm unless absolute. Line numbers describe the files read during this analysis; another agent may subsequently change them.

**What one frame costs.** At the measured 1032×535 raster, one image is 552,120 pixels: 2,208,480 bytes (2.11 MiB) as ARGB, before PNG. At ~12/s this is 6.63 million pixels/s and 26.5 MB/s for just one traversal of the raw images. Capture, format conversion/flip, copying, PNG row conversion/filtering and comparison traverse or allocate additional storage. The ~76 kB PNG is ~29:1 smaller than raw ARGB; five application chunk headers add 205 bytes, before WebSocket/TCP/IP overhead. ~76 kB × 12 = ~912 kB/s agrees with the supplied ~911 kB/s active observation. There is no extra audio streaming load.

The only defensible CPU-per-frame estimate from the supplied A/B is the older 512-frame case: (45%−14%)/12 ≈ **25.8 ms of aggregate CPU time per capture** attributable to attaching the viewer, assuming those matched runs and cadence represent steady state. This includes all viewer-related work, not just compression, and CPU time is not serial wall latency. It cannot be transferred to 128. At 128, ~130% is **1.3 cores across the whole process**, not “130% audio callback load.” The clean no-viewer 128 baseline is unknown. Subtracting the old 14% baseline would fabricate attribution. Separate stage wall/CPU timings are needed to quote encoder milliseconds or a measured percentage saving.

**Actual pipeline:**

1. `mdRemotePanelV3.cpp:60-130`: owner-thread geometry/gesture work, hard-coded 66,667 µs capture gate on a 20 ms timer, no-client early return, bounded screenshot request and a full `image.createCopy()` into a newest-only pending slot. `takeScreenshot` schedules a render and permits one outstanding screenshot (`source/juceRmlUi/juceRmlComponent.cpp:1187-1205`). Thus even an unchanged panel can force rendering.
2. Backend matters. OpenGL does `glReadPixels`, allocates a second image and flips it (`juceRmlComponent.cpp:365-385`). Metal requests capture and converts returned RGBA bytes into JUCE ARGB (`:470-496`). Software uses `RendererJuce::captureFrame` (`:1250-1257`; `source/juceRmlUi/rmlRendererJuce.cpp:1747`). Screenshot callbacks are delivered in `RmlComponent::update` (`:1001-1009`). The live renderer was not identified by the supplied measurements; do not diagnose a GPU stall or assume software rasterization from aggregate CPU alone.
3. `mdRemotePanel.cpp:94-98`: a separate worker checks for a pending capture then sleeps 5 ms. `mdRemotePanelV3.cpp:132-158`: only widths above 1100 are resized; **1032×535 is not downscaled at all**. Every pending capture then goes through JUCE PNG encoding. Only afterward are encoded bytes compared against `m_lastPng`. Equal output suppresses publication, not rendering/capture/compression. Generation and 750 ms freshness checks protect publication.
4. `mdRemotePanelServer.h:20-24,48-57` and `mdRemotePanelV3.cpp:181-197`: immutable full PNG per in-progress client, global newest image, intermediate frame coalescing, 16,384-byte chunks. The current frame is finished before the next latest frame starts. `mdRemotePanelWire.h:29-37` supplies the byte limiter. `mdRemotePanelServer.cpp:422-469` drains controls then sends at most one panel chunk per wake; the pump wakes writers approximately every 3 ms (`mdRemotePanel.cpp:474,499-504`). Thus five chunks also require several service opportunities even if all tokens exist.
5. `/Users/michaelmeneses/gearmulator-ipad-panel/web/panel3.js:218-255`: allocate a complete PNG buffer, collect chunks, make an image/png Blob, decode via createImageBitmap or Image, then paint and acknowledge. Geometry maps raster back into host context (`:119,132-139,201-213`). A server raster reduction therefore needs no new hit-test map. Faster delivery should also harden `done()` at `:239-246`: asynchronous results currently lack a generation/monotonic-sequence recheck, and old bitmaps/object URLs are not explicitly released. At higher rates, prevent stale decode completion from overwriting newer pixels; keep one decode in flight plus newest pending complete frame. This is a real client-code issue, not evidence of an observed failure.

**Dirty-region transport is a separate, higher-risk extension**, not the existing v2 LCD tile protocol. For sparse LCD/LED/button changes it could cut both compression work and frame bytes much more than whole-frame downscale. However, computing a CPU diff after capture still pays full capture cost. Patches require a base-frame sequence, explicit rectangles, generation validation, atomic completed-update presentation, resynchronization keyframes, and coalescing against each client's actual base. Dropping intermediate dependent patches without rebuilding against that base corrupts the display. Keep lossless full keyframes for first/recovery frames. A true idle period must not receive gratuitous periodic keyframes. `doc/remote-panel-v3.md:225-235` expressly defines independent full PNGs today, so this requires an extension/negotiation, not silent reuse of the existing layout.

**Freshness trap:** simply backing idle capture off beyond 750 ms triggers `mdRemotePanel.cpp:487` source-unavailable and releases contacts. Initially retain a sub-750 ms health capture with equality suppression, or deliberately redesign the watchdog to validate live renderer progress independently of pixel changes. Idle purity concerns transmitted frame bytes; occasional unchanged health captures can satisfy it while costing less CPU.

**An additional latency lever that does not save encode CPU:** allow a bounded whole-keyframe burst while keeping the average byte cap, chunk size and between-chunk control priority. A ~96 KiB bucket (or a measured one-frame allowance with a hard maximum) lets a ~76 kB changed frame after sufficient idle credit avoid ~35 ms of artificial pacing. Waking for remaining token-eligible chunks can remove the extra ~3 ms gaps; do not busy-spin when empty or enqueue unbounded bytes into TCP. Existing limiter/server code makes this a small host-side change with no wire/client visual change. It increases instantaneous traffic and must pass streamed RTT and audio checks. It does not make sustained 30×76 kB/s fit: that needs ~2.29 MB/s before transport headers, or ≤~41.5 kB/frame at 30/s under the current rate, with headroom. Fitting a frame into the current burst is stricter still: roughly 32.6 kB including application overhead.

## A3 - Is a 128-frame audio block actually safe here?

**128 is a plausible low-latency candidate, not yet demonstrated dropout-free. 256 is my provisional playing default; 512 is the fallback if measured deadline tails demand it.** None is formally qualified by aggregate CPU or a short symbol sample. Do not change the user's live 128 setting for this analysis.

At 44.1 kHz, 128/256/512 give 2.902/5.805/11.610 ms callback periods and approximately 345/172/86 callbacks/s. Per-sample emulation work is broadly unchanged by subdivision; per-callback costs are paid 4× as often at 128 as at 512: host bus setup, lock acquisition, MIDI handling, resampler entry, queue housekeeping, instrumentation and panel publication. There may also be bursty compilation or state work. The code shows a blocking device mutex around processing (`source/synthLib/plugin.cpp:98-158`), synchronous hardware rendering (`source/elektron/md/mdLib/mddevice.cpp:666-677`), and buffer clearing/conversion plus scheduler advance (`mdhardware.cpp:1158-1194,1615-1628`). These are reasons to measure the distribution, not to assert that short blocks multiply all engine work by four.

A useful model is T(N)=cN+h+jitter. For the supplied M4 JIT real-time ratio 0.775 at 512, a hypothetical proportional 128 callback still consumes 77.5% of its deadline; it does **not** need to finish the old 512 block inside a 128 period. Conversely, fixed h becomes four times larger as a fraction of the budget. In that simplified model, r128=0.775+3h/(512/fs); the spare 22.5% only tolerates h<0.075×(512/fs), about 0.87 ms if fs=44.1 kHz, before average ratio reaches 1. This is an illustrative bound, not a fitted overhead estimate: the engine benchmark and live host callback may have different rates, content and overhead. The measured 0.775 is capacity context, not a live p99 guarantee. The single-digit DSP counts in the capture-on profile neither convict nor exonerate the engine.

**The frame-sync spin loop is not an obvious MD optimization target.** `source/dsp56300/source/dsp56kEmu/jitops_jmp.cpp:49-65` implements `esaiFrameSyncSpinloopBra`: it immediately returns unless peripherals are **Peripherals56362**, recognizes a branch-to-self testing ESAI transmit-frame-sync, and emits a call which fast-forwards emulated time (`:8-30`). It is already an idle-loop optimization, not a host-side “sleep until the audio callback” or a missed-deadline recovery mechanism. Crucially this MD Dsp owns **Peripherals56303** (`source/elektron/md/mdLib/mddsp.h:56,88`), so this particular BRA specialization is not the MD runtime fast path. The neighboring JMP specialization includes 56303 ESSI handling (`jitops_jmp.cpp:92-134`). Do not remove polling or arbitrarily skip emulated cycles: scheduler, link, interrupt and firmware timing depend on them. A JIT code-generation symbol in a sample can also mean compilation rather than generated code executing in the audio callback.

**When a block runs late:** `Hardware::advance` loops `schedStep()` until the requested emulated interval completes (`mdhardware.cpp:1615-1624`); there is no wall-clock deadline bailout here that returns perfect audio and catches up later. `renderHostAudio` drains carry, advances the requested chunk and copies available output (`source/elektron/md/mdLib/mdhostaudioqueue.h:152-183`), with bounded surplus, not an unlimited latency reservoir. Falling behind wall time makes the host/device run out of timely samples. The audible result can be clicks, crackle, discontinuities, repeated or silent fragments, and sustained stutter under persistent overload; the exact concealment is device/host dependent. Separately, an emulated codec producing too few samples can leave pre-cleared output zeros—this is not the same as an OS scheduling xrun. Increasing screen traffic can worsen either lock/scheduling headroom without increasing the DSP's mathematical workload.

## A4 - Ranked recommendation

**First ship a bounded whole-keyframe burst in the v3 sender.** This is my single best first change for felt latency in the measured setup: it removes a code-proven artificial ~35 ms serialization floor for an ordinary ~76 kB frame, without increasing capture frequency or PNG encoding work on a process already measured near 130% CPU at 128. Keep the Mac emulator, genuine rendered pixels, raw multitouch, resolution and lossless PNG unchanged.

Concretely, increase `PanelBudget`'s maximum credit from 32,768 to a bounded ~96 KiB, provide appropriate first-frame credit, retain the 1,250,000 B/s refill rate and 16,384-byte chunks, and promptly service remaining token-eligible chunks while checking the control queue between each. Schedule a refill wake when tokens are insufficient; never busy-spin. Retain newest-frame coalescing and a single immutable frame in progress. A full burst is a maximum, not permission to queue unlimited stale frames. The existing ~3 ms pump gaps otherwise consume roughly four gaps for five chunks; increasing credit alone can still help, but prompt bounded draining realizes more of the gain. Update the documented burst policy in `doc/remote-panel-v3.md:244-249`; the binary PNG/chunk layout and viewer can remain compatible. No change is made here.

Why this ahead of raising cadence: at ~12×76 kB/s, average traffic (~0.91 MB/s) already fits the 1.25 MB/s budget; it is the **small burst allowance** that stretches an individual frame. More capture alone cannot overcome that and adds CPU competition. This first change has a narrowly testable benefit: encode-ready→complete-PNG-received falls, with the same capture and encoding workload. It may save on the order of tens of milliseconds, not a promised exact subtraction from both 34/68 ms observations. Real Wi-Fi/TCP may limit the gain; a larger burst could worsen downstream ack/pong queueing, which is why B is a shipping gate. Preserve control priority, but acknowledge that it cannot preempt bytes already in TCP.

**Second, make capture respond to actual visual changes, then qualify a higher active cadence.** Begin with raw-pixel equality before compression and a scoped faster PNG encoder benchmark; retain the best total encode-plus-transfer result, not merely the fastest compressor. Add a render-change-triggered capture opportunity so a new pressed state or firmware update does not wait behind the present ~80 ms capture phase. Coalesce rapid changes, never wait for a TouchAck round trip, and keep capture/encode off the audio thread. Initially keep the current sustained rate ceiling, permit a prompt interaction frame by borrowing a later capture slot, and keep a quiet health capture safely inside the 750 ms deadline. Wire idle must remain exactly zero bytes. This can improve isolated gestures without paying a constant 30-fps idle bill.

Then test 20–30/s during real activity only after stage timing and audio tails demonstrate headroom. At 30/s, keep average full-frame bytes below ~41.5 kB with margin under the present rate (and smaller still if retaining the old burst); otherwise change the rate limit deliberately after measuring the LAN or introduce negotiated lossless dirty regions. Try a modest 825-pixel raster only if needed and only if LCD text remains comfortably legible. Avoid committing simultaneously to compression, raster, cadence and codec changes: measure each so the benefit is attributable. The future 30/s target is conditional; it is not a switch already present in this tree.

**Audio configuration accompanies those changes, rather than replacing them.** For a newly qualified release, use 256 as a provisional default and offer 128 once its measured deadline/output checks pass on the intended device; leave the current live session alone. On Model 12, moving 256→128 saves ~2.9 ms in reported output latency and ~1.45 ms of ideal mean block phase. Those are useful for playing, but the first screen-path change plausibly addresses tens of milliseconds without shortening the audio deadline. Going 512→128 would give a larger benefit (~8.7 ms device presentation plus ~4.35 ms ideal mean block phase), but the current session is already at 128. Optimizing 22 µs hit-testing cannot compete with either.

I therefore agree that the screen likely dominates the **feeling of a laggy panel**, with an important qualification: the supplied sound-path data do not measure finger-to-acoustic onset or Wi-Fi. A percussionist can be sensitive to even a few milliseconds of audible delay, so screen improvement does not excuse missed audio deadlines or excessive sound latency. The recommendation follows the identified screen wait and its low-risk removal, not merely a comparison of unlike measurements.

**Do not:** blindly set capture to 60 fps; remove the byte budget; send every captured frame through a deep FIFO; use PNG level 0 as a quick fix; start with a codec rewrite; reconstruct a fake client panel or optimistic machine state; return to A10 emulation; alter DSP spin loops on the basis of the mixed profile; or call 128 “safe” from process CPU alone. Retain Mac-owned audio and the already-working two-handed ownership/hit-testing semantics. The settled product needs a faster presentation pipeline and measured audio headroom, not a new architecture.

## B - Falsification

These are proposed acceptance experiments, not experiments performed during this read-only analysis. Keep the current live session untouched; use existing passive records where available and run controlled A/Bs in a later agreed test window. Record the exact source/build, device, actual sample rate/block size, renderer, raster, song/kit, display state and viewer count. Do not compare a Model 12 baseline with Mac mini Speakers as if only the code changed.

**1. Falsify the first change at its claimed stage.** For unchanged PNG size and capture cadence, record per-frame capture completion, encode start/end, first/last chunk admission/send, byte count and token waits on the host; record complete-frame receive, decode start/end and canvas draw on the iPad. Associate exact generation/sequence and the first frame containing the causal changed pixels, not simply the next received frame. Host-local encode-ready→last-chunk-send should lose the token-starvation plateau for frames that fit the new accumulated allowance. Client-local first→last chunk arrival should contract. Cross-machine encode-ready→receive needs synchronized clocks with a reported error bound; otherwise use those local segments and the physical end-to-end measurement. No clock subtraction shortcut.

Repeat randomized-phase Function/Kit downs and ups, chords and knob motion under idle-then-touch and sustained activity. Aim for at least 200 physical trials per condition and report median/p95 plus uncertainty; more trials are needed to interpret p99 robustly. A high-speed camera must show contact and the specific changed pixels together. A host pressed overlay is not proof of a firmware LCD change: report those separately. Faster server sends with unchanged physical touch-to-screen distribution would falsify the claim that this change improves felt screen latency—remaining capture/render/decode/display or Wi-Fi dominates. No reduction in the host token-wait stage would mean the implementation or the assumed limiter attribution is wrong. A rising stale-frame age, worse touch/pong RTT tails, or older decoded frames overwriting newer frames rejects the change even if nominal fps rises.

As a proposed shipping target, seek a repeatable screen p50 improvement of at least ~10 ms with no p95 regression beyond the measurement uncertainty; this is an acceptance choice, not a prediction. If the gain is below camera resolution or run-to-run variation, call it inconclusive and profile the next stage. Inspect actual PNG sizes in any trial apparently beating A1's size-dependent floor.

**2. Idle purity is exact: zero PanelFrame bytes over 30 seconds.** After handshake/recovery completes and all pending frames drain, leave a genuinely unchanged panel with the viewer connected for 30 s. Count binary **0x85 PanelChunk** bytes at the existing viewer (PanelFrame is the conceptual full image, not a separate v3 wire ID). Required result: byte delta **0**, completed panel-frame delta **0**, and no unsolicited source loss/recovery. Host `panelBytes` and `panelFrames` should also remain frozen, but host counters count built payloads and are not sufficient delivery proof. Pongs, JSON diagnostics and v2 LCD traffic are outside the PanelFrame count. Do not use the viewer's total `bytesIn` as a panel-only metric. Do not attach a second v3 viewer just to measure: that changes the workload. Start only after release styling/animations settle; a running sequencer with blinking LEDs is not an unchanged-panel idle test. Any periodic PNG/keyframe byte, even one, fails this criterion. The historical zero-byte result is evidence for the existing implementation, not a pass for proposed code.

Also verify that the optimized idle loop is actually cheaper: capture/encode counts and stage CPU should drop as intended, while idle source availability remains live beyond 750 ms. Zero transmitted bytes with unchanged full-speed capture/PNG work satisfies wire purity but falsifies a claim of cheaper idle capture.

**3. Audio is a hard gate, including raised cadence.** At the same audio setting, compare baseline ~12/s with proposed 20/s and 30/s active capture in separate matched windows, holding scene/activity and instrumentation fixed. Include idle viewer, continuous encoder movement, two-handed chords, LCD/menu activity and the user's demanding playing material. Record actual requested/accepted/completed/encoded/sent/displayed rates: “30 requested” is not “30 displayed.” For every condition report full-callback D p95/p99/max, duration/budget ratios, over-budget counts, late-start/inter-arrival gaps, longest consecutive late run, driver overload/xrun delta and observed output discontinuities. Include a sufficient run length and sample count: 10 min at 128/44.1 kHz is ~206,719 callbacks. Full-callback recording must be complete with no drops; biased slow-callback logs cannot supply true p95/p99.

A cadence increase from ~12 to 30/s is **2.5× capture work if cost per capture is unchanged**. It may reduce screen phase yet steal CPU/memory bandwidth, lengthen UI/device-lock contention or delay the audio thread. There is no reliable numeric prediction for the resulting audio p95/p99/max from the supplied process CPU. Measure those tails explicitly rather than predicting they stay flat. Require no new audio discontinuities or hardware overloads, no new deadline misses, and no reproducible tail regression that consumes the chosen safety margin. A conservative candidate gate is p99 below 80% of the callback budget and max below one budget over the stated run, with independent late-start/output checks; 80% is an engineering margin, not an established universal safe threshold. At 128/44.1 kHz that proposed p99 target is ~2.32 ms. If p95 improves but p99/max or xrun count worsens, reject the cadence change. If the baseline already fails, neither variant is qualified; a relative improvement does not turn dropouts into a pass.

**4. Reject false improvements and regressions in correctness.** Compression tuning fails if larger PNGs cancel its encode-time saving or overflow the 2 MiB cap. Downscaling fails if LCD glyphs/labels are illegible at actual iPad size, or geometry mapping/edge touches change. Change-driven capture fails if autonomous LCD/LED updates, desktop interaction, release states or overlays stay stale, or a stationary hold loses its 400 ms encoder-press semantics. Any stuck contact, lost two-finger ownership, stale-generation display/input, blank recovery, decode backlog or unbounded memory growth rejects shipping. Higher throughput makes the existing asynchronous decode completion guard/resource-lifetime issue more urgent; test recovery and monotonically displayed sequences after fixing it.

**5. What would change the priority order.** If exact per-frame timings show little token wait for the causal ~76 kB frames, or the burst patch does not reduce physical latency, move render/capture scheduling ahead of transport. If GPU/software capture dominates frame cost, prioritize render-dirty capture/readback over compression tuning. If sound onset is the user's actual limiting delay and measured network/firmware/audio latency exceeds screen delay, prioritize that measured sound-path term. If 128 passes callback/output checks under worst active streaming, qualify it; if it fails and 256 passes, ship 256 regardless of the lower reported 128 outputLatency. The 128/no-viewer CPU baseline remains explicitly unknown until a matched no-viewer window is available.
